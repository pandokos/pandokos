# Sprint 12.3 — Implementation plan

- Design: [sprint.md](sprint.md). Section numbers (§) refer to it; T-numbers are its tests, D-numbers
  its decisions, G- and F-numbers its findings, O-numbers its open points.
- Each part below is self-contained: an agent needs sprint.md and that part only. Parts run in order
  A, B, C1 … C7, D, E, F.
- Suggested grouping: **G1** = C1, C2 (the declarative document); **G2** = C3 (configuration alone);
  **G3** = C4 (upgrade); **G4** = C5, C6, C7 (the drill, in that order). After part B the four
  groups do not depend on each other. A, B, D, E and F are one agent each. Because the risk class is
  high: C6 (the recovery script and the key cases) and C4 (the traffic assertions) are reviewed by
  an agent that did not write them, with §5.5, §5.6 and §5.9 as the checklist; and **part E1 (the
  backup guide) is reviewed step by step against the suite by an agent that did not write either**
  (R-1).

## Rules for the implementer

1. Work on the branch the orchestrator names; do not create one. Every commit is signed off in the
   maintainer's name (`git commit -s`; the identity is the one of the repository's git
   configuration, never changed or overridden) and keeps the signature the configuration asks for
   (`commit.gpgsign`, SSH): never disable it. No co-author line, no attribution line, no tool
   footer, no link to a session and no mention of an assistant or of a model in any commit message,
   pull request title or description, comment, review, release text, footer or file. One commit for
   A, one for B, one per step of C (message given with the step), one for D, one for E, one for F
   if something is found.
2. **No migration, no change to `api/openapi/admin.v1.yaml`, no permission, no error code, no new
   module** in `go.mod` or in a nested module, **no GitHub Action that the workflows do not already
   use**. If something seems to need one, stop and ask.
3. **Never invent a commit hash, a digest, a version or an address.** Action pins are copied from
   `.github/workflows/ci.yml` as they stand. The PostgreSQL 16 and OpenBao digests are copied from
   `test/db/compose.yaml` and `test/transit/compose.yaml`. The three values of `test/upgrade/PREVIOUS`
   and the digest of the later PostgreSQL major come from the commands of A2 and A3, run by you.
4. **The drill is destructive by design and only inside what it created.** No test of `test/drill`
   reads a database address, a key service address or a container name from the environment; it
   talks only to the Compose project it started, by the ports it read back. The recovery script is
   run only there. Never run `make test-drill` cleanup commands with a project name you did not
   generate.
5. **No secret anywhere:** credential values, signing secrets, key files, unseal shares, tokens and
   passwords are generated by the test at run time, registered with the canary collector, kept in
   `t.TempDir()`, and never written to a fixture, a golden file, the report, a log line of the
   test, or the record. Never print the content of a key file, a secret file of `--secrets-out`, a
   dump or a snapshot.
6. **The guide is corrected only by a finding.** When a step of `backup-and-restore.md` does not
   work as written, record it (G-n, continuing from G-7) with the command and what happened, change
   the guide in part E1, and make the suite execute the corrected text. Do not adapt the suite
   silently, and do not improve the guide beyond what a finding names.
7. **Observe before you fix** for T-1131, T-1142 and T-1143: write the test, run it on the code as
   it is, keep what it showed for the record (part E2), then implement or document.
8. New tests of the default suite follow CONTRIBUTING: `dbtest.NewMigrated`, `t.Parallel()` first,
   port 0, no shared mutable package variable. Do not change the helpers of `test/e2e`.
