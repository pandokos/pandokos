# 0047. Identity providers in the test suite

- Status: accepted
- Date: 2026-11-16

Refines [ADR 0018](0018-supply-chain.md). [ADR 0023](0023-test-dependencies-in-nested-modules.md) does not
apply: no third-party Go module is needed.

## Context

IAM-06 asks that tokens of real identity providers are accepted, and the epic asks for tests with two
open-source providers; a third, Authentik, was added afterwards. Faults (an outage, a rotated key, an oversized key set) and forged tokens cannot
be produced by a real provider, and tokens and keys must not be stored in the repository.

## Decision

- **An in-process issuer**, `test/fakeidp`, with keys generated when the test runs, serves everything that
  needs faults or forged tokens: discovery, key set, a signer for arbitrary headers and claims, refusal,
  delay, oversize, key rotation, request counting.
- **Keycloak, Ory Hydra and Authentik in containers**, behind the build tag `idp` in the root module, in one CI job
  `idp` (built from the steps of the `test` job that start the database, then `make idp-up` and
  `make test-idp`). A test behind the tag fails, never skips, when a provider is missing. Pinned by digest,
  so that a Dependabot update is a reviewed change:
  - `quay.io/keycloak/keycloak:26.8.2@sha256:c68e286cacd87b942ac1939a0a1481461109d6acd3a57dc496969a319a76bbf0`
  - `oryd/hydra:v26.2.0@sha256:ff67c7fb5f95074fa53374d41151713554960504b340cd3f95b09e65deaea2a9`
  - `ghcr.io/goauthentik/server:2026.8.5@sha256:602227a86455d6772e3d16b7d852713c4f864f40df5df894abd1285bb53979a5`
    (the digest of the multi-architecture index; server and worker use the same image)
  - `postgres:16-alpine@sha256:aa6cb33cf4c19c765cefcf48d96176258800870a9a1e930ad126200f9d825139` for
    Authentik's database (the image of `test/db`); Authentik needs no Redis at this version
- **Keycloak** carries the platform-level scenario. It starts with `--http-enabled=false`; the realm is
  rendered by `up.sh` to `local/idp/keycloak-realm.json` and mounted at
  `/opt/keycloak/data/import/pandokos.json`. Clients have `fullScopeAllowed=false` and
  `directAccessGrantsEnabled=false`. Tokens are RS256, `aud` is a string, `sub` a generated UUID, `azp` and
  `client_id` carry the client ID, the lifetime is 300 s, there is no `nbf`, and a claim mapper adds the
  organisation as `pandokos_org`. Its key set includes an RSA-OAEP key with `use: enc`, which `internal/jwks`
  drops.
- **Hydra** carries the tenant-bound scenario. It is configured by environment: `DSN=memory`,
  `SECRETS_SYSTEM`, `URLS_SELF_ISSUER` (with a trailing slash), `URLS_LOGIN`, `URLS_CONSENT`,
  `SERVE_PUBLIC_PORT`, `SERVE_PUBLIC_TLS_ENABLED=true`, `SERVE_PUBLIC_TLS_CERT_PATH`,
  `SERVE_PUBLIC_TLS_KEY_PATH` and `STRATEGIES_ACCESS_TOKEN=jwt`. Its admin API is plain HTTP on port 4445
  inside the container and is not published. Clients are created with `docker compose exec hydra hydra
  create client --endpoint http://127.0.0.1:4445 --id ... --secret ... --token-endpoint-auth-method
  client_secret_post --audience ...`. Tokens are RS256 (its key set has two `use: sig` keys), `typ` is `JWT`,
  `aud` is an array, `sub` equals the client ID, the lifetime is 3599 s and `nbf` and `iat` are present. A
  request without the `audience` parameter gives `aud: []`, which Pandokos refuses; an audience outside the
  client's list is refused by Hydra (`invalid_request`).
- **Authentik** carries a platform-level and a tenant-bound scenario on one issuer. It runs as `server`
  and `worker` on its own PostgreSQL. `AUTHENTIK_SECRET_KEY`, the database password, the bootstrap
  password and token (`AUTHENTIK_BOOTSTRAP_PASSWORD`, `AUTHENTIK_BOOTSTRAP_TOKEN`) and the app passwords
  are generated by `up.sh`. `AUTHENTIK_LISTEN__HTTP`, `__HTTPS` and `__METRICS` are set to `0.0.0.0:...`,
  because the defaults bind `[::]`, which a container without IPv6 refuses (the server exits). The
  server serves HTTPS on 9443; the configuration is the blueprint `test/idp/authentik-blueprint.yaml`,
  mounted in `/blueprints/custom` and read by the worker, which holds no secret (`!Env` for the
  passwords, `!File` for the certificate of `up.sh`). It sets that certificate as the web certificate
  of the default brand, creates the provider `pandokos-tests` and its application, four service
  accounts (`workload-a`, `-b`, `-c`, `-unmapped`) with the attribute `pandokos_org` and an app password
  each, and a scope mapping `pandokos` that returns `pandokos_org` from the user's attribute. Settings
  that differ from what the documentation suggests and that the provider needs: `grant_types:
  [client_credentials]` (empty by default, and then every request is `invalid_grant`), a non-empty
  `redirect_uris` (required by the schema, never used), the built-in "authentik Self-signed Certificate"
  (RSA, generated by Authentik) as signing key (without it tokens are HS256), `sub_mode: user_username`
  and `access_token_validity: minutes=5`. The server reads the web certificate when it starts and
  notices a change only minutes later, so `up.sh` waits until the blueprint is in the database and then
  restarts the server once. The client-credentials request carries `client_id`, `client_secret`,
  the service account's `username` and app password as `password`, and `scope=pandokos` (a scope
  mapping applies only to a requested scope); with the user name and password the client secret is not
  checked, and without them the token is that of the pseudo-user `ak-pandokos-tests-client_credentials`.
  The issuer is `https://localhost:<port>/application/o/pandokos-tests/` (per provider, with a trailing
  slash, built from the request's host), the token endpoint is the global
  `/application/o/token/`, and the key set is `<issuer>jwks/`. Tokens are RS256 (`typ` `JWT`), `aud` is
  a string equal to the client ID and no other audience can be requested, `sub` is the user name of the
  service account (the default `hashed_user_id` is an opaque hash), `azp` is the client ID, the lifetime
  is 300 s, `iat` and `auth_time` are present and `nbf` is not. The key set holds one RSA 4096 key, with
  `use: sig`, `alg: RS256`, `x5c` and `x5t`. The same `iss` is in the token and the discovery document.
  The tenant is chosen by the claim `pandokos_org`; "another audience" is tested by registering the
  issuer with a different audience, not by a different token.
- **Mechanics.** Neither Keycloak nor Hydra has a shell or curl, so the compose file has no healthcheck for them
  and `up.sh` polls with curl from the host (Authentik's images carry their own healthcheck). `up.sh` chooses free ports with `python3`, generates a certificate (the
  directory `local/idp` is mode 0700 and git-ignored, and `server.key` is mode 0644 inside it because the
  containers run as other users) and per-client secrets, writes `local/idp/env`, and runs `docker compose
  down -v` first, because Hydra's store is in memory. Authentik takes two to four minutes to start
  (database migrations), the others seconds. `make idp-up`, `make test-idp` and `make idp-down`
  follow the pattern of `make db-up`.
- **No key, token or client secret in the repository.** A test (T-R37) scans for token-shaped strings and
  private key blocks.

## Consequences

- Each update of either provider runs against Pandokos before it is merged, and the documents of each
  pinned version are tested unchanged against `internal/jwks`.
- Five containers more in one CI job, Authentik being the slow one; `make check` does not run them.
- Providers other than the three are not tested; the guide marks them so.

## Alternatives considered

**Dex.** No client-credentials grant in v2.45.1.
**Zitadel.** Needs its own database.
**Recorded tokens.** They expire, and they would be secrets in fixtures.
**A nested module with a Go OIDC client.** Not needed: the tests are plain HTTP against the binary.
