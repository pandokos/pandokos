# 0071. Webhook destinations: the signature, the signing secrets and egress

- Status: accepted
- Date: 2026-11-23

**Amends** [ADR 0033](0033-vault-formats-and-key-identifiers.md) (the vault seals a second kind of object) and
extends [ADR 0038](0038-egress-guard-upstream-tls-and-proxy.md) to a fourth caller of the egress guard. Builds on
[ADR 0054](0054-usage-data-is-the-tenants.md) and [ADR 0070](0070-the-outbox-as-a-log-relay-by-destination-and-retention.md).
Requirement EVT-04; sprint 6.4.

## Context

A tenant's events leave Pandokos for a URL the tenant chose. That is an outbound request made on behalf of a
tenant administrator (a way to reach an internal address), it carries the tenant's usage data, and the receiver
must be able to tell a genuine request from a forged one. The secret that makes a request believable must be kept
as well as a provider credential, and nothing may write it to a log.

## Decision

1. **The request.** `POST` of the CloudEvents document with `Content-Type: application/cloudevents+json;
   charset=utf-8` and the three headers of the Standard Webhooks specification: `webhook-id` (the event ID),
   `webhook-timestamp` (seconds since the epoch, when the attempt is made) and `webhook-signature`
   (`v1,<base64 of HMAC-SHA256(key, "<id>.<timestamp>.<body>")>`). An existing library of the receiver's language
   verifies it. A receiver refuses a timestamp more than five minutes from its clock and a signature that matches
   no valid key. The response body is read up to 64 KiB and discarded; only the status is kept; a `3xx` is a
   failure (`redirect`).
2. **Secrets are generated by the server** (32 random bytes, shown once as `whsec_<base64>` when the destination is
   created or its secret rotated, never again); a caller cannot supply one. During a rotation the previous secret
   stays valid for a time the caller chooses (24 hours by default, at most 7 days) and `webhook-signature` carries
   two signatures separated by a space.
3. **Sealed under the tenant's data key** with associated data of their own kind (`pandokos/webhook-secret/v1`,
   the tenant, the destination, the data key version): `vault.SealNamed` and `OpenNamed`. A credential's
   ciphertext does not open as a signing secret, nor one destination's as another's. **This amends ADR 0033**: the
   vault seals a second kind of object, with its own associated data, beside provider credentials. The worker opens
   a secret for one round; at the end of the round it zeroes the 32 bytes of the signing key and the buffers of the
   vault and of the parser. The plaintext text `whsec_…` is a Go string (`secret.Secret`), which cannot be
   zeroed: it is left to the garbage collector. The admin role cannot read the sealed columns (column grants, as for
   provider credentials): it seals a new secret and a trigger keeps the replaced one as the previous one. A secret is
   a `secret.Secret` from generation to the HMAC; the shape `whsec_…` joins the shapes the log handler redacts;
   it appears in no audit row, log line, error or export, and in no response but the two that show it once.
   Destroying the tenant's data key (ADR 0067) destroys the secrets.
4. **Egress.** Requests go through the egress guard (ADR 0038, its fourth caller): the public transport (`https`,
   public addresses checked on the address dialled, TLS 1.2 or later with verification, the outbound proxy when one
   is configured), **no redirect followed**, one deadline (`events.delivery.timeout`). A host listed in
   `events.webhook.private_hosts` uses the private transport and may be `http`; the list is the operator's.
   `internal/outbox` builds no transport, dialer or TLS configuration (a repository test keeps it so). The URL is
   `https`, at most 2048 characters, no user information or fragment, and is configuration, not a secret: every
   holder of `event_destination:read` reads it, and the audit log keeps its host only.
5. **The test request** is recorded by the administration and sent by the worker: the admin process makes no
   webhook request and opens no signing secret. The administration answers `202`; the worker sends one
   `io.pandokos.destination.test.v1` event, to a disabled destination too, and records the outcome and status on
   the destination. The event is not written to the log and moves no cursor.
6. **What the roles can do.** The worker holds no `UPDATE` on `url`, `event_types`, `enabled` or a secret, so it
   cannot redirect a tenant's events; the admin role cannot read a sealed secret nor forge a delivery history. A
   tenant has at most 8 destinations.

## Consequences

- A receiver can use an existing library, and the repository carries an independent example and a test that the
  two agree.
- A leaked secret lets a third party forge events to that tenant's receiver; it does not read the tenant's data.
  Rotation with an overlap replaces it without a gap.
- The signing secrets need the key file, so only a worker that has it can deliver (sprint 8.2); with an external
  key service (sprint 12.1) opening a secret needs a data key cache of the opener.
- The platform's events have no webhook: the vault seals under tenants' data keys and the platform has none.

## Alternatives considered

**Asymmetric signatures** (a key registry for receivers): more to publish and rotate, and the specification above
is widely implemented.

**Mutual TLS** (per-destination certificates): certificate management for every receiver.

**A secret supplied by the caller**: weak secrets, and a secret in a request body or a declarative document.

**The administration sends the test request**: it would have to open a signing secret, which the admin role must
never do.
