# Release v0.1.0 — Core BYOK

Acceptance check of 2026-11-16, made on the commit that carries this page (the last commit of sprint
4.1). The tag `v0.1.0` is pushed by the maintainer on the commit of `main` that holds this page; the
page is what the maintainer pastes or links as the release text (`release.yml` attaches
`api/openapi/admin.v1.yaml` and the SBOM and writes a fixed note).

## What v0.1.0 is

The first release of Pandokos, the R1 sentence of [requirements §4](../requirements/README.md): run
one container with PostgreSQL, create tenants and virtual keys, store BYOK credentials, call OpenAI
and Anthropic through stock SDKs with streaming, and read a usage record with cost for every call.
Callers authenticate with a virtual key or with a token from a trusted issuer.

**It is not for production.** There are no rate limits or budgets (epic 5), no sign-in for people
(the administration API takes keys only, epic 4.2), and one process. Treat it as a reference to try,
to review and to build on.

## What is in

- **Epic 1, foundations** ([record](../history/epic-01-foundations/README.md)): the signed container
  and its pipeline, PostgreSQL with forced row-level security and three runtime roles, the
  isolation harness, service accounts, virtual keys, authorization, the audit log, the
  administration API and the CLI.
- **Epic 2, vault and catalogue** ([record](../history/epic-02-vault-and-catalogue/README.md)):
  BYOK credentials under per-tenant keys, write-only; providers, endpoints, models, grants and
  versioned prices from the open dataset.
- **Epic 3, gateway** ([record](../history/epic-03-gateway/README.md)): OpenAI and Anthropic
  passthrough with streaming, the egress guard, one usage record per call, spans over OTLP,
  OpenAI-compatible providers by configuration, SDK suites, the Compose reference.
- **Sprint 4.1, trusted token issuers** ([sprint](../../planning/epics/04-identity-and-rbac/4.1-trusted-token-issuers/sprint.md),
  [tokens.md](../operations/tokens.md), ADRs 0045 to 0047): JWTs from registered issuers
  (tenant-bound, or platform-level with the tenant in a claim and an explicit list) authenticate
  inference calls through explicit subject mappings; keys are fetched by the gateway with caching;
  tested against Keycloak and Hydra (Authentik was added afterwards).

## Known limits

- A NUL character in the `description` of resources older than sprint 4.1 (for example service accounts) returns 500 instead of 400; fixing it needs a shared mapper of SQLSTATE 22021.
- No rate limits, budgets or concurrency limits (epic 5; GW-16 has size and duration only). Calls
  that fail upstream are not retried (by design, GW-11).
- Tokens are accepted on the inference listener only; the administration API takes keys only and no
  one signs in as a person (epic 4.2). Subject rules match exactly; there are no scopes per mapping
  and no check operation for a registration (4.1 open points O-1, O-4, O-5, O-7). Platform-level
  token failures before the tenant is known are logged, not audited (O-8). Two tenants sharing an
  issuer must use an audience that names the tenant ([tokens.md](../operations/tokens.md)).
- Only the built-in roles `tenant-admin` and `inference` and the platform admin; recovery of a
  tenant that lost every admin key is not offered (sprint 4.3, AZ-09).
- The key-encryption key is a local file; it is not rotated by the product and an external KMS comes
  in R3 (VLT-10, VLT-12). The vault's limits and recovery procedure are a draft (VLT-16).
- Tamper evidence of the audit log is not provided (AUD-04, R2); metrics are not exported, only
  traces (OBS-01); one process, with the admin plane able to reach the key (OPS-05, epic 8).
- Tenant deletion, reports and export of the audit log arrive with epic 6. Usage answers over 4 MiB
  are estimated; several currencies are not converted.
- The Compose reference is one host with a self-signed certificate and no backup of the key file.
- Providers other than OpenAI, Anthropic and OpenAI-compatible endpoints are not supported; the
  manual check of compatible providers ([providers.md](../operations/providers.md)) ships "not yet
  run".

## Upgrade notes

None: this is the first release. The database schema is created by migrations 0001 to 0008
(`pandokos migrate`). An operator starting from an earlier development build provides a key file
(`pandokos kek generate`) and removes the `skeleton.*` settings, as the records of epics 2 and 3
say.

## How to verify the image

The image `ghcr.io/pandokos/pandokos:0.1.0` (also `0.1` and `latest`) is signed with cosign
(keyless), with an SPDX SBOM and a SLSA provenance attestation. The commands are in
[container.md](../operations/container.md#verifying-a-release).

## Maintainer actions outside the repository

1. Push the tag `v0.1.0` on the commit of `main` that holds this page.
2. After the workflow ends, verify the tagged release's signature, SBOM and provenance with the
   commands of [container.md](../operations/container.md) (the `verify` job does the same in CI).
3. Run the manual provider check of [providers.md](../operations/providers.md) against Groq, Mistral
   and Ollama with real keys and fill its table.
4. Read this page and decide whether the rows verified only in CI (criterion 1 among them) are acceptable; paste or link this page as the release text.
