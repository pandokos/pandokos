# Release v0.1.1 — fix of the parsing of integer settings

A fix release of [v0.1.0](v0.1.0.md), cut from the maintenance branch `release/0.1`. The tag `v0.1.1`
is pushed by the maintainer on the commit of `release/0.1` that holds this page; the page is what the
maintainer pastes or links as the release text (`release.yml` attaches `api/openapi/admin.v1.yaml`
and the SBOM and writes a fixed note).

## What v0.1.1 is

v0.1.1 changes one thing in the program: how a setting that holds an integer is read from the
configuration. It adds no feature, no setting, no migration and no change to the administration API.
Everything said about v0.1.0 in its [release page](v0.1.0.md), including **it is not for
production**, holds for v0.1.1.

## What is fixed

Code scanning (CodeQL, rule `go/incorrect-integer-conversion`) flagged six places of
`internal/config/keys.go` where an integer setting was read as a 64-bit number and then converted to
`int` without a check. On a 32-bit build a value that does not fit in 32 bits was silently wrapped
(`4294967297` became `1`) instead of being refused, and the wrapped value was the one that reached
the range check of the setting.

Each integer setting is now read at the width of the field it sets:

- the settings that set an `int` (`listeners.inference.max_header_bytes`,
  `listeners.admin.max_header_bytes`, `database.gateway.max_connections`,
  `database.admin.max_connections`, `database.worker.max_connections`) are read at the width of
  `int` on the platform, so a value that does not fit is refused with the usual "not an integer"
  error;
- `limits.max_request_body_bytes`, which sets an `int64`, is read as a 64-bit number on every
  platform.

**Who is affected.** The images of Pandokos are `linux/amd64` and `linux/arm64`, where `int` has 64
bits: for them the behavior does not change, and a value accepted by v0.1.0 is accepted by v0.1.1.
The fix matters to whoever builds Pandokos from source for a 32-bit platform. No vulnerability is
involved: the settings are written by the operator, not by a caller.

The change reaches `release/0.1` by pull request
[#42](https://github.com/pandokos/pandokos/pull/42), a cherry-pick of the fix merged into `main` by
[#41](https://github.com/pandokos/pandokos/pull/41). It adds a test, `TestParseIntWidth`
(`internal/config/parse_int_test.go`), that runs on both widths: `GOARCH=386 go test ./internal/config`
exercises the 32-bit case. The setting `limits.default_output_tokens` that `main` also covers does
not exist on this branch and is not part of this release.

## Documentation and deployment files

The release pins what a reader runs to the release itself, so that a document never describes a
version other than the one it ships with:

- the quick start of the README clones the tag (`git clone --branch v0.1.1`) instead of `main`, so the
  deployment files are the ones of the release;
- the default image of `deploy/compose/compose.yaml` stays the moving tag `0.1`, which the release
  workflow moves to `0.1.1`, so that a patch release reaches an installation without a change of the
  files;
- the README status, the Compose guide and `SECURITY.md` name v0.1.1.

`test/repo` checks it from now on against the newest page of `docs/releases/`: a release whose page
exists but whose README, quick start, Compose guide or security policy still name an older version
fails the tests ([`release_test.go`](../../test/repo/release_test.go)).

## Upgrade notes

From v0.1.0: an installation that runs the image `0.1` (the Compose default) gets `0.1.1` by pulling
it again; one that names `0.1.0` replaces it with `0.1.1`. The
database schema is the one of v0.1.0 (migrations 0001 to 0008); `pandokos migrate` has nothing new to
apply. No setting changes name or meaning; a 64-bit build, which is every published image, reads
every value as before.

## How to verify the image

The image `ghcr.io/pandokos/pandokos:0.1.1` (also `0.1`; `latest` is moved to the newest release that
is not a pre-release) is signed with cosign (keyless), with an SPDX SBOM and a SLSA provenance
attestation. The commands are in [container.md](../operations/container.md#verifying-a-release).

## Maintainer actions outside the repository

(The steps of every release are in [CONTRIBUTING.md](../../CONTRIBUTING.md#releasing).)

1. Check that the scan of `release/0.1` reports no open alert of the integer conversion.
2. Push the signed tag `v0.1.1` on the commit of `release/0.1` that holds this page.
3. After the workflow ends, verify the signature, SBOM and provenance of `0.1.1` with the commands
   of [container.md](../operations/container.md) (the `verify` job does the same in CI).
4. Paste or link this page as the release text.
