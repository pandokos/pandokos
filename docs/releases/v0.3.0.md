## What v0.3.0 is

The third release of Pandokos, theme **Ready to operate**, the R3 sentence of
[requirements §4](../requirements/README.md): deliver usage events to an external system, keep the key-encryption key
in an external service, rely on a reviewed threat model, a tested restore and a stated upgrade policy.

Relative to [v0.2.0](v0.2.0.md): usage and limit events leave Pandokos by signed webhook, or are pulled over the API,
and every call yields one (sprint 6.4); the key-encryption key can live in the transit engine of an OpenBao or
HashiCorp Vault service, so that none is on the Pandokos hosts (sprint 12.1); the threat model was reviewed against the
code and every parser of network input is fuzzed (sprint 12.2); the restore is executed by a test suite, the upgrade
from v0.2.x is tested under traffic and has a policy, and an installation is what its configuration and its
declarative documents say (sprint 12.3). The Docker Compose reference deployment runs PostgreSQL 18.

**It is a pre-1.0 release with breaking changes** (next section). Before 1.0 a minor version may break
compatibility, and only the latest minor version is supported. **It is not for production**: limit counters are per
instance (epic 8), there is no multi-factor authentication and no independent security assessment yet (epic 10), the
maintainer's own walk of the restore in a lab has not been made at the time of the acceptance check, and the review of
the threat model was made by the people who wrote the code; see "Known limits".

## Breaking changes compared with v0.2

Read this section before upgrading. Each item says what an operator or an integrator must do.

1. **A request body with a member in another case is refused** (sprint 12.2,
   [ADR 0074](../adr/0074-threat-model-review-and-continuous-fuzzing.md)). A member that differs only in case from
   one the gateway reads (`Model` beside `model`, `Stream` beside `stream`, and the others of the two families,
   `stream_options.include_usage` included) is answered with `400 invalid_request`, as an invalid request is today;
   the reason `member_case` is in the operator's log. A body without such a member is forwarded byte for byte as
   before. *Do:* an integration that sends such a body must send one spelling.
2. **The Compose reference deployment moves to PostgreSQL 18** (`postgres:18-alpine`, pinned by digest, instead of
   16). The `pgdata` volume made by PostgreSQL 16 cannot be opened by the 18 image, which also mounts the volume at
   `/var/lib/postgresql`: `docker compose up` on it fails at `postgres`. *Do:* an existing Compose installation
   moves its database **before** it takes the new `compose.yaml`: stop Pandokos, dump with the 16 server, start the
   new server on a new volume, restore the dump, start Pandokos and verify both audit chains
   ([the steps](../operations/compose.md#moving-an-installation-from-postgresql-16-to-18)). Installations that run
   their own PostgreSQL are not affected: 16 and later are supported.
3. **`deploy/postgres/recover-lost-kek.sql` also disables event destinations.** The script of the recovery after a
   lost key-encryption key now disables the event destinations whose signing secret was sealed under the lost
   version and prints three counts; the owner rotates the secret and enables the destination. *Do:* if you have the
   script in a runbook, copy the new one and add the step ([backup and restore guide](../operations/backup-and-restore.md)).
4. **Migration `0017_events` does not run next to the old binary.** An instance of v0.2 that runs while `migrate`
   runs turns not ready (`/readyz` answers `503 not_ready`) and refuses to start again on the new schema; the new
   binary refuses a schema that is not migrated. *Do:* stop every instance, `pandokos migrate`, start the new binary
   (see "Upgrade notes"). There is no down migration: going back is a restore.

The key service is new in this release, so its refusal of an exportable key (`vault.kek.transit.allow_exportable_key`, sprint 12.2) breaks nothing that v0.2 ran. Everything else is an addition: five permissions, twelve operations under the tag `events` and nine configuration
keys (sprint 6.4), fourteen configuration keys, four instruments and seven log lines (12.1), the sections of the
declarative document (12.3). The only change of the API document besides the operations of 6.4 is its version:
`info.version` of `api/openapi/admin.v1.yaml` is `0.3.0`. Sprints 12.1 to 12.3 add no migration, no permission, no
operation and no error code.

### Sprint 6.4, events for external systems ([events guide](../operations/events.md), [event reference](../reference/events.md); [ADR 0070](../adr/0070-the-outbox-as-a-log-relay-by-destination-and-retention.md), [0071](../adr/0071-webhook-destinations-signature-secrets-and-egress.md), [0072](../adr/0072-event-types-the-envelope-the-external-reference-and-platform-events.md))

Usage and limit events leave Pandokos by signed webhook, or are pulled over the API, in CloudEvents 1.0.

- **Events.** Nine types: `usage.recorded`, `limit.threshold_reached`, `limit.exhausted` (a tenant's log) and
  `tenant.deletion_requested`, `tenant.deletion_cancelled`, `tenant.deleted`, `kek.version_activated`,
  `kek.version_retired` (the platform's log), each with a published JSON Schema in `docs/reference/events/`. The
  database writes them in the transaction of the fact.
- **Destinations.** A tenant registers up to 8 signed webhooks (Standard Webhooks headers, a signing secret shown
  once, rotation with an overlap), tests them, rewinds them, and replays dead letters. Delivery is at least once,
  with backoff and a dead-letter state. An example receiver is in `examples/webhook-receiver`.
- **Pull.** `pandokos event export` and `pandokos platform-event export`; the sequence of the last line is the
  cursor.
- **The external reference** of a tenant, set by the platform, is carried by every event.
- **Five permissions:** `event_destination:read`, `event_destination:write`, `event_destination:delete`,
  `event:read`, `platform_event:read` ([permissions](../reference/permissions.md)).
- **Twelve operations** under the tag `events` and the commands `event-destination`, `event`, `platform-event`
  and `event schema`; the document has 179 operations.
- **Nine configuration keys**, `events.*` ([configuration reference](../operations/configuration.md)).
- **Seven instruments** (`pandokos.events.*`) and six log lines.
- **Migration `0017_events`**, applied by `pandokos migrate`.

### Sprint 12.1, external key-encryption key ([external key guide](../operations/external-key.md); [ADR 0073](../adr/0073-the-transit-key-provider.md))

The key-encryption key can live in a key service instead of a file: the transit secrets engine of OpenBao or of
HashiCorp Vault. Installations that keep a key file are not affected.

- **The provider.** `vault.kek.provider: transit` wraps and unwraps the data keys of tenants in the service, which
  never exports the key. Pandokos sends seven requests over HTTP, with no vendor library, through the egress
  guard, and never rotates, configures, trims or deletes the key. Associated data are bound by the service (as a
  SHA-256 digest, so no tenant identifier reaches it), and the binding is proved at every start by a negative
  probe: a service that ignores the field, as HashiCorp Vault 1.8 to 1.12 do, is refused.
- **Two services, tested.** Every change runs the same conformance suite against `openbao/openbao:2.7.3` and
  `hashicorp/vault:2.2.2` (images pinned by digest, in development mode) and against a test double; expected to
  work from OpenBao 2.0 and HashiCorp Vault 1.13.
- **Authentication.** A token or an AppRole, read from files; Pandokos renews the token, logs in again, and adopts
  a replaced token file. Namespaces are sent as `X-Vault-Namespace` (OpenBao). A least-privilege policy is in
  `deploy/transit/pandokos-policy.hcl`.
- **Version identifiers** come from an HMAC the service computes under each key version
  (`transit-<16 hex>-v<N>`), wrapped keys use the format `0x02`, and a rotation in the service takes effect at the
  next restart.
- **Moving.** Both providers can run at once, for unwrapping, so an installation moves from the key file to the
  service and back by the re-wrap of release 0.2, one instance or several.
- **On failure.** One attempt per request with a deadline of 2 s, at most 32 requests in flight, a refusal of 5 s
  after five consecutive unavailable answers; callers without a cached key get `503` with `Retry-After: 5`. `serve`
  waits for the service at start, listening on nothing, and starts by itself when it answers
  (`vault.kek.transit.start_timeout` sets a limit); `/readyz` does not depend on the service once started. The
  worker's event relay opens signing secrets through a cache of unwrapped keys.
- **`pandokos kek check`** authenticates, describes the key and runs the probe without touching the database, and
  prints the provider, the version, the range of versions the service can unwrap and the weak settings.
- **Fourteen configuration keys**, `vault.kek.transit.*` (thirteen of this sprint and `allow_exportable_key` of 12.2;
  [configuration reference](../operations/configuration.md)).
- **Four instruments**, M59 to M62 (`pandokos.vault.provider.requests`, `.request.duration`, `.up`, `.token.ttl`),
  with no address, name, namespace or version as an attribute; **seven log lines** (`key provider ready`,
  `configuration weak`, `unavailable`, `recovered`, `token expiring`, `authentication failing`, `no longer needed`),
  the field `kek_unwrap_provider` on `vault ready`, and the value `kek_provider_unavailable` of `cause`.
- **No new error code, permission or operation:** the API document is unchanged by this sprint.

### Sprint 12.2, threat model review and continuous fuzzing ([security model](../architecture/security-model.md), [review record](../architecture/threat-model-review-2026-11.md); [ADR 0074](../adr/0074-threat-model-review-and-continuous-fuzzing.md))

The security model was reviewed against the code for the first time: every boundary, statement and threat now has an
identifier, the code of its control and the tests that prove it, and a record states what the review found.

- **Three behaviours change**: a request body with a member in another case is refused, an exportable key of the key
  service is refused unless allowed (breaking change 1; the second is new with the key service), and **a release is verified by digest**: the release
  page prints `ghcr.io/pandokos/pandokos@sha256:<digest>`; verify that digest and run it
  ([container guide](../operations/container.md#verifying-a-release)). The tag is for a first trial.
- Four instance and pod credential addresses join the forbidden class of the egress guard (the EKS Pod Identity
  agent in IPv4 and IPv6, the Google Compute Engine metadata server in IPv6 and the OpenStack metadata service in
  IPv6, [gateway guide](../operations/gateway.md), section 6).
- **34 fuzz targets**, every parser of network input among them, run on every pull request and every night, with
  nightly vulnerability scans of the repository and of the released image and a nightly reading of the repository's
  rulesets (`scheduled.yml`); the published image is scanned before it is released; two more secret shapes are
  scanned for in the history.
- There is no migration, no change of the API document, no new permission and no new error code.

### Sprint 12.3, restore drill, upgrade policy and an instance by configuration alone ([restore drill record](../operations/restore-drill-2026-11.md), [upgrade guide](../operations/upgrade.md), [backup guide](../operations/backup-and-restore.md); [ADR 0075](../adr/0075-upgrade-policy-and-the-tested-upgrade.md), [0076](../adr/0076-the-restore-drill-its-record-and-recovery-after-a-lost-key.md), [0077](../adr/0077-an-instance-defined-by-configuration-alone.md))

- **The restore is tested.** A suite (`make test-drill`, a job on every pull request) executes the backup guide
  against servers it starts and destroys: a logical and a physical restore into an empty server, both audit chains
  verified after a restore, a restore on PostgreSQL 18, the four cases of the key with a key file and with
  OpenBao, and a deletion replayed after a restore. The guide was corrected where the drill found it wrong: the
  check of the audit heads (`audit export --to-seq`, then `audit verify --file`), the database of a dump (created
  with the database guide's grants), the reading of a backup older than a rotation, and the effect of a new key on
  events.
- **The recovery script disables destinations** (breaking change 3).
- **A key service is backed up by its snapshot**, taken after every rotation and before Pandokos is restarted;
  never trim a version a kept backup needs; keep the unseal shares with the snapshot.
- **The upgrade.** The supported upgrade is from any patch of the previous minor, and a patch release has no
  migration. The interval without service measured by the upgrade test on one instance was 1.0 s (indicative). Going
  back is a restore.
- **An installation by configuration alone.** Every configuration key has a scope in the reference; the ambient
  environment the process reads is listed; the declarative document gains platform-level issuers with their tenants,
  tenant issuers, subject mappings, destinations and the external reference (`apply --secrets-out DIR` creates a
  destination and writes its secret once to a file). Nothing to do for a document you already have.
- There is no migration, no change of the API document, no new permission and no new error code.

## Known limits

From the records of epics 6 and 12 and the sprint files of 6.4 and 12.1 to 12.3; the limits of
[v0.2.0](v0.2.0.md#known-limits) that these sprints do not lift still hold. Lifted by this release: limit events and the events
of a tenant's deletion and of a key rotation are delivered to other systems, the restore is drilled, and platform and
tenant token issuers and subject mappings are in the declarative document.

- **Limit counters are per gateway instance**; several instances each enforce alone until epic 8 (shared counters).
- **No multi-factor authentication and no independent security assessment** (epic 10, release v1.0.0). The review of
  the threat model was made by the people who wrote the code and shares their blind spots; the
  [review record](../architecture/threat-model-review-2026-11.md) lists what was not reviewed and the residual
  exposures the maintainer accepted, among them that the scraper's `platform-auditor` key reads more than metrics, that
  whoever holds the key service's token and the database unwraps every data key while the token lives, and that a
  fuzz crash shows its stack trace in a public log before it is fixed.
- **The maintainer's own walk of the restore** (a full run in a lab, backup and restore included, following the
  corrected guides) was not made at the time of the acceptance check: the drill record is of the automated drill alone
  until it is. The drill did not cover HashiCorp Vault's snapshot (OpenBao is the tested reference), a backup store's
  own encryption, a pooler in front of the target, a ledger at scale (epic 10), a restore by someone who did not write
  the guide, a physical restore across a later major (PostgreSQL refuses it) and a cluster of key service nodes.
- **Events:** delivery is at least once, and "no event is lost" holds while the event is in the log, that is for
  `events.retention` (168 hours by default), delivered or not. After a restore a receiver may see identifiers it
  already saw (at least once, from the backup's cursor), the sequence numbers after the backup are issued again with
  new identifiers, and a puller's cursor must be reset ([drill record](../operations/restore-drill-2026-11.md), finding G-7).
  There is no webhook for the platform's log (it needs a platform data key; an issue), only a pull. Audit rows are not
  events (`audit.recorded`, the "forwarded" of AUD-06, is not built), nor are `limit.unlimited_traffic`, a change of
  active currency, refused grants and refused support attempts. A URL with a token in its path is readable by every
  holder of `event_destination:read`. Webhook hosts that are `http` or private must be listed in
  `events.webhook.private_hosts`.
- **The cost on the ledger's insert:** each usage record also writes an event. On the development machine of sprint
  6.4 a batch of 500 records took a median 108.7 ms without the trigger and 145.5 ms with it (ratio 1.34,
  `TestOutboxWriteCost`); the figure on production hardware is for sprint 10.1.
- **The key service:** only the transit engine of OpenBao and HashiCorp Vault (expected from OpenBao 2.0 and HashiCorp
  Vault 1.13); cloud key services (AWS KMS, Google Cloud KMS, Azure Key Vault) are issue #75, after v1.0; Kubernetes
  authentication to the service is sprint 8.2. A rotation in the service takes effect at the next restart. A process
  started during an outage listens on no port until the service answers.
- **The upgrade is stop, migrate, start**, with an interval without service (1.0 s measured on one instance with
  small data, indicative); rolling upgrades with two versions serving at once are decided with the work on replicas
  (epic 8). Only the upgrade from the previous minor is supported: from v0.1.x go through v0.2.0.
- **The restore of a dump and of a base backup** needs the key-encryption key versions of the backup (or, with a key
  service, its snapshot and unseal shares); a backup older than a rotation opens credentials until its key version is
  destroyed; the tenants whose data keys were under a lost version enter their credentials again and their destinations'
  signing secrets are rotated.
- **The Pandokos image of the Compose reference follows a moving minor tag** (`0.3`); production runs the digest.
  The SBOM on the release page is an unsigned copy of the attested one, and the signature of the tag is checked by the
  maintainer and not by the workflow.
- **A reference deployment on PostgreSQL 18** is a different major from the one of the earlier releases: see
  breaking change 2.

## Upgrade notes

From v0.2.x (schema of migrations 0001 to 0016). Upgrading from v0.1.x is not supported directly: go through v0.2.0
([upgrade guide](../operations/upgrade.md#2-the-supported-upgrade)). The steps, in order:

1. **Read "Breaking changes" above**, and back up the database, the key file of every `active` or `retiring` version
   (or, with a key service, its snapshot) and the configuration, and keep the heads of the audit chains with their
   `seq` ([backup and restore guide](../operations/backup-and-restore.md)). There is no down migration: the backup
   is how you go back.
2. **Check the configuration with the new binary:** `pandokos config check` run with the **new** binary against the
   **current** configuration must exit 0.
3. **Stop every instance, run `pandokos migrate`, start the new binary.** One migration is crossed,
   `0017_events` (sprint 6.4). Instances of v0.2 that keep running turn not ready and must be stopped; started again
   they refuse the newer schema. The interval measured by the upgrade test on one instance with small data was
   1.0 s (indicative).
4. **Check:** `pandokos migrate status` exits 0, `/readyz` answers 200 on both listeners, `vault ready` in the log
   names the same `kek_version` with `kek_activation: unchanged`, a call with a tenant's key reaches the provider, and
   both audit chains verify.
5. **Events start with the migration: nothing is produced for the past.** `0017_events` revokes nothing. Each usage
   record also writes an event (the cost on the ledger's insert is in "Known limits"). Events are kept for
   `events.retention` (168 hours by default), delivered or not; an event an enabled destination had not received by
   then is removed and counted, and the events of a tenant not delivered when its deletion begins are removed with
   it. Webhooks leave from the worker role through the egress guard; hosts that are `http` or private must be listed
   in `events.webhook.private_hosts`. Register destinations when you want them (`pandokos event-destination`); with
   none, the events are written and expire.
6. **New configuration keys**, all optional ([configuration reference](../operations/configuration.md)): `events.*`
   (nine, sprint 6.4) and `vault.kek.transit.*` (fourteen, sprints 12.1 and 12.2); every key now has a scope,
   `instance` or `installation`, and the settings of the second kind must be identical on every instance. Nothing
   to do for an installation that keeps a key file: it runs the code it ran before and builds neither the router of
   providers nor the cache of unwrapped keys.
7. **The key-encryption key does not change at the upgrade.** To move to a key service afterwards, follow the
   [external key guide](../operations/external-key.md), run `pandokos kek check` first, and with several instances
   configure the service on every instance before any instance wraps with it. A process that waits for the service at
   start listens on no port: give an orchestrator's probe a start-up allowance.
8. **Permissions:** the five new permissions are held by the built-in roles as the [permission reference](../reference/permissions.md)
   says; a custom role that should manage destinations or read events is granted the permissions it needs. The platform sets
   a tenant's external reference with `tenant create|update --external-reference`.
9. **If you use the recovery script** after a lost key, take `deploy/postgres/recover-lost-kek.sql` of this release
   (breaking change 3).
10. **A Compose installation** moves its database from PostgreSQL 16 to 18 **before** it takes the new `compose.yaml`
    (breaking change 2), then does steps 1 to 4 with the image `0.3`; the two can be done at the same time, as
    the [Compose guide](../operations/compose.md#moving-an-installation-from-postgresql-16-to-18) says. Other
    installations on PostgreSQL 16 stay on it.
11. **A patch release of 0.3 has no migration** and removes or renames no configuration key: it is installed by
    replacing the binary.

## How to verify the image

The image `ghcr.io/pandokos/pandokos:0.3.0` (also `0.3`; `latest` is moved to the newest release that is not a
pre-release) is signed with cosign (keyless), with an SPDX SBOM and a SLSA provenance attestation. **Verify it by its
digest and run it by digest:** after the release workflow ends, the digest of the version tag is printed by
`docker buildx imagetools inspect ghcr.io/pandokos/pandokos:0.3.0` and the image to name in a Compose file or a
manifest is `ghcr.io/pandokos/pandokos@sha256:<digest>` (this page is committed before the tag exists, so the digest of
the release is pasted into the release text by the maintainer after verification). The commands are in
[container.md](../operations/container.md#verifying-a-release).
