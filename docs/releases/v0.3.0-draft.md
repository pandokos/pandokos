# Release v0.3.0 (draft)

A draft of the notes of the next release, kept current by each sprint of epic 6 and later; it is not a release
page and no tag exists. The final page replaces it when the release is cut. The previous release is
[v0.2.0](v0.2.0.md).

## PostgreSQL 18 in the reference deployment

The Docker Compose reference deployment runs PostgreSQL 18 (`postgres:18-alpine`, pinned by digest) instead of 16
([Compose guide](../operations/compose.md)); the minimum stays PostgreSQL 16, and CI now runs the whole test suite
on both: the job `test (pg18)` runs `go test -race ./...` with the release toolchain on PostgreSQL 18, beside the
floor jobs that stay on 16 ([ADR 0075](../adr/0075-upgrade-policy-and-the-tested-upgrade.md)).

### Upgrade notes

- **An existing Compose installation must move its database before it takes the new `compose.yaml`.** The `pgdata`
  volume made by PostgreSQL 16 cannot be opened by the 18 image (which also mounts the volume at
  `/var/lib/postgresql`): `docker compose up` on it fails at `postgres`. Stop Pandokos, dump with the 16 server,
  start the new server on a new volume, restore the dump, start Pandokos and verify both audit chains: the steps
  are in the [Compose guide](../operations/compose.md#moving-an-installation-from-postgresql-16-to-18), and rest on
  the restore on a later major that the [drill](../operations/restore-drill-2026-11.md) ran.
- Installations that run their own PostgreSQL are not affected: 16 and later are supported.

## Threat model review and continuous fuzzing (sprint 12.2)

The security model was reviewed against the code for the first time: every boundary, statement and threat now has an
identifier, the code of its control and the tests that prove it, and a record states what the review found
([security model](../architecture/security-model.md), [review record](../architecture/threat-model-review-2026-11.md),
[ADR 0074](../adr/0074-threat-model-review-and-continuous-fuzzing.md)).

Three behaviours change:

- **A request body with a member in another case is refused.** A member that differs only in case from one the
  gateway reads (`Model` beside `model`, `Stream` beside `stream`, and the others of the two families) is answered with
  `400 invalid_request`, as an invalid request is today; the reason `member_case` is in the operator's log. A body
  without such a member is forwarded byte for byte as before.
- **An exportable key of the key service is refused unless allowed.** `serve` and `pandokos kek check` refuse a key
  that was created `exportable` with a message that names `vault.kek.transit.allow_exportable_key`, the new key (the
  fourteenth of the block, after the thirteen of sprint 12.1, default `false`). Set it to accept such a key knowingly, and for the whole of a move
  from or to it ([external key guide](../operations/external-key.md)). Installations with a key file or with a key that
  is not exportable are not affected.
- **A release is verified by digest.** The release page prints `ghcr.io/pandokos/pandokos@sha256:<digest>`; verify
  that digest and run it ([container guide](../operations/container.md#verifying-a-release)). The tag is for a first trial.

Also in this release: four instance and pod credential addresses join the forbidden class of the egress guard (the
EKS Pod Identity agent in IPv4 and IPv6, the Google Compute Engine metadata server in IPv6 and the OpenStack
metadata service in IPv6, [gateway guide](../operations/gateway.md), section 6); 34 fuzz targets, run on every pull
request and every night, with nightly vulnerability scans of the repository and of the released image and a nightly
reading of the repository's rulesets; the published image is scanned before it is released; two more secret shapes
are scanned for in the history. There is no migration, no change of the API document, no new permission and no new
error code.

## Restore drill and upgrade policy (sprint 12.3)

The restore is tested, the upgrade from v0.2.x is tested and has a policy, and an installation can be described by
its configuration and documents alone ([restore drill record](../operations/restore-drill-2026-11.md),
[upgrade guide](../operations/upgrade.md), [backup guide](../operations/backup-and-restore.md),
[ADR 0075](../adr/0075-upgrade-policy-and-the-tested-upgrade.md), [ADR 0076](../adr/0076-the-restore-drill-its-record-and-recovery-after-a-lost-key.md),
[ADR 0077](../adr/0077-an-instance-defined-by-configuration-alone.md)).

- **The restore is tested.** A suite (`make test-drill`, a job on every pull request) executes the backup guide
  against servers it starts and destroys: a logical and a physical restore into an empty server, both audit chains
  verified after a restore, a restore on PostgreSQL 18, the four cases of the key with a key file and with
  OpenBao, and a deletion replayed after a restore. The guide was corrected where the drill found it wrong:
  the check of the audit heads (`audit export --to-seq`, then `audit verify --file`), the database of a dump
  (created with the database guide's grants), the reading of a backup older than a rotation, and the effect of
  a new key on events. The drill record is the one linked above; the maintainer's manual walk (a full run in a lab,
  backup and restore included, following the corrected guide) is made after epic 12 closes and before the tag.
- **The recovery script disables destinations.** `deploy/postgres/recover-lost-kek.sql` now also disables the
  event destinations whose signing secret was sealed under the lost version and prints three counts; the owner
  rotates the secret and enables the destination.
- **A key service is backed up by its snapshot**, taken after every rotation and before Pandokos is restarted;
  never trim a version a kept backup needs; keep the unseal shares with the snapshot.
- **The upgrade.** The supported upgrade is from any patch of the previous minor. Upgrading from v0.2.x crosses one
  migration, `0017_events`: back up, `pandokos config check` with the new binary, stop, `pandokos migrate`, start,
  check (`kek_activation: unchanged`). The interval without service measured by the upgrade test on one
  instance was 1.0 s (indicative). A patch release has no migration. Going back is a restore.
- **An installation by configuration alone.** Every configuration key has a scope in the reference; the ambient
  environment the process reads is listed; the declarative document gains platform-level issuers with their tenants,
  tenant issuers, subject mappings, destinations and the external reference (`apply --secrets-out DIR` creates a
  destination and writes its secret once to a file). Nothing to do for a document you already have.
- There is no migration, no change of the API document, no new permission and no new error code.

## External key-encryption key (sprint 12.1)

The key-encryption key can live in a key service instead of a file: the transit secrets engine of OpenBao or of
HashiCorp Vault ([external key guide](../operations/external-key.md)). Installations that keep a key file are not
affected. The block `vault.kek.transit.*` has thirteen keys.

- **The provider.** `vault.kek.provider: transit` wraps and unwraps the data keys of tenants in the service, which
  never exports the key. Pandokos sends seven requests over HTTP, with no vendor library, through the egress
  guard, and never rotates, configures, trims or deletes the key. Associated data are bound by the service (as a
  SHA-256 digest, so no tenant identifier reaches it), and the binding is proved at every start by a negative
  probe: a service that ignores the field, as HashiCorp Vault 1.8 to 1.12 do, is refused.
- **Two services, tested.** Every change runs the same conformance suite against `openbao/openbao:2.7.3` and
  `hashicorp/vault:2.2.2` (images pinned by digest, in development mode) and against a test double; expected to
  work from OpenBao 2.0 and HashiCorp Vault 1.13.
- **Authentication.** A token or an AppRole, read from files; Pandokos renews the token, logs in again, and adopts
  a replaced token file. Namespaces are sent as `X-Vault-Namespace` (OpenBao). A least-privilege policy is in
  `deploy/transit/pandokos-policy.hcl`.
- **Version identifiers** come from an HMAC the service computes under each key version
  (`transit-<16 hex>-v<N>`), wrapped keys use the format `0x02`, and a rotation in the service takes effect at the
  next restart.
- **Moving.** Both providers can run at once, for unwrapping, so an installation moves from the key file to the
  service and back by the re-wrap of release 0.2, one instance or several.
- **On failure.** One attempt per request with a deadline of 2 s, at most 32 requests in flight, a refusal of 5 s
  after five consecutive unavailable answers; callers without a cached key get `503` with `Retry-After: 5`. `serve`
  waits for the service at start, listening on nothing, and starts by itself when it answers
  (`vault.kek.transit.start_timeout` sets a limit); `/readyz` does not depend on the service once started. The
  worker's event relay opens signing secrets through a cache of unwrapped keys.
- **`pandokos kek check`** authenticates, describes the key and runs the probe without touching the database, and
  prints the provider, the version, the range of versions the service can unwrap and the weak settings.
- **Fourteen configuration keys**, `vault.kek.transit.*` ([configuration reference](../operations/configuration.md)).
- **Four instruments**, M59 to M62 (`pandokos.vault.provider.requests`, `.request.duration`, `.up`, `.token.ttl`),
  with no address, name, namespace or version as an attribute; **seven log lines** (`key provider ready`,
  `configuration weak`, `unavailable`, `recovered`, `token expiring`, `authentication failing`, `no longer needed`),
  the field `kek_unwrap_provider` on `vault ready`, and the value `kek_provider_unavailable` of `cause`.
- **No new error code, permission or operation:** the API document is unchanged.

### Upgrade notes

- There is no migration: no migration, table, policy or grant changes in this sprint.
- Nothing to do for installations with a key file: they run the code they ran before and build neither the router of
  providers nor the cache of unwrapped keys.
- To move to a key service, follow the [external key guide](../operations/external-key.md), run `pandokos kek
  check` first, and with several instances configure the service on every instance before any instance wraps with
  it. A process that waits for the service at start listens on no port: give an orchestrator's probe a start-up
  allowance.

## Events for external systems (sprint 6.4)

Usage and limit events leave Pandokos by signed webhook, or are pulled over the API, in CloudEvents 1.0
([events guide](../operations/events.md), [event reference](../reference/events.md)).

- **Events.** Nine types: `usage.recorded`, `limit.threshold_reached`, `limit.exhausted` (a tenant's log) and
  `tenant.deletion_requested`, `tenant.deletion_cancelled`, `tenant.deleted`, `kek.version_activated`,
  `kek.version_retired` (the platform's log), each with a published JSON Schema in `docs/reference/events/`. The
  database writes them in the transaction of the fact.
- **Destinations.** A tenant registers up to 8 signed webhooks (Standard Webhooks headers, a signing secret shown
  once, rotation with an overlap), tests them, rewinds them, and replays dead letters. Delivery is at least once,
  with backoff and a dead-letter state. An example receiver is in `examples/webhook-receiver`.
- **Pull.** `pandokos event export` and `pandokos platform-event export`; the sequence of the last line is the
  cursor.
- **The external reference** of a tenant, set by the platform, is carried by every event.
- **Five permissions:** `event_destination:read`, `event_destination:write`, `event_destination:delete`,
  `event:read`, `platform_event:read` ([permissions](../reference/permissions.md)).
- **Twelve operations** under the tag `events` and the commands `event-destination`, `event`, `platform-event`
  and `event schema`; the document has 179 operations.
- **Nine configuration keys**, `events.*` ([configuration reference](../operations/configuration.md)).
- **Seven instruments** (`pandokos.events.*`) and six log lines.

### Upgrade notes

- Migration `0017_events` is applied by `pandokos migrate`. **Events start with it: nothing is produced for the
  past.** It revokes nothing.
- **The cost on the ledger's insert:** each usage record also writes an event. On the development machine of the
  sprint a batch of 500 records took a median 108.7 ms without the trigger and 145.5 ms with it (ratio 1.34;
  `TestOutboxWriteCost`, `make bench`); measure on your hardware.
- **The bound of EVT-03:** events are kept for `events.retention` (168 hours by default), delivered or not; an
  event an enabled destination had not received by then is removed and counted. Events of a tenant not delivered
  when its deletion begins are removed with it.
- Webhooks leave from the worker role through the egress guard; hosts that are `http` or private must be listed in
  `events.webhook.private_hosts`.
